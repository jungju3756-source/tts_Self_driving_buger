# LiDAR SLAM + VSLAM 병행 계획 (라파 2대 구성)

> 작성 2026-10-07 · 상태: **계획만 정리함. 이번 주에는 진행하지 않음**
> 배경: 교수님 지시로 LiDAR SLAM 과 VSLAM 을 함께 진행한다 (팀원 찬영과 같은 과제).
> 카메라: Intel RealSense **D405** (LeRobot 에서 쓰던 것을 받을 예정)

---

## 1. 목표
- 지금 쓰는 **LiDAR SLAM**(Cartographer 지도 + AMCL)에 **카메라 기반 VSLAM**을 더한다.
- 두 방식을 같은 방에서 비교하고, 가능하면 **융합**한다.
- 기존 기능은 그대로 유지한다: 음성으로 장소 이동, 장애물 회피, 웹 조종석.

## 2. 왜 라파를 하나 더 쓰나
- **CPU**
  - 라파1은 지금도 bringup, AMCL, Nav2, 음성, 웹을 돌리느라 CPU를 약 30 % 씁니다. Nav2 composition을 적용한 뒤 수치입니다.
  - 오늘 무거운 계산 하나만 추가로 돌려도 Nav2가 느려져 주행에 실패했습니다.
  - VSLAM(영상 특징점 추출, 루프 클로저)은 CPU를 많이 써서 같은 Pi에 올리기 어렵습니다.
- **전력**
  - 로봇 5 V 공급원(OpenCR)이 Pi 5, LiDAR, 웹캠, 터치 화면(구매 예정)을 모두 감당하고 있습니다.
  - 여기에 D405(스트리밍할 때 약 1.55 W)와 VSLAM 연산까지 더하면 여유가 거의 없습니다.

## 3. 구성 (안)

```
 ┌──────────────── 라파1 (jungju4, 기존) ────────────────┐      ┌──────── 라파2 (신규) ────────┐
 │ OpenCR · LDS-02 · C920 · (터치 화면)                   │      │ RealSense D405 (USB 3)       │
 │ bringup · AMCL · Nav2 · Cartographer(지도 만들 때)      │ ◄──► │ realsense2_camera            │
 │ voice_ptt · place_manager · web 조종석                 │ Wi-Fi │ VSLAM (RTAB-Map 후보)        │
 └────────────────────────────────────────────────────────┘ DDS  └──────────────────────────────┘
              같은 ROS_DOMAIN_ID=40 · 같은 TF 트리 (base_link ─ camera_link)
```

| 항목 | 라파1 | 라파2 |
|---|---|---|
| 역할 | 주행 · 위치 추정 · 음성 · 웹 (지금과 같음) | 카메라 드라이버 · VSLAM |
| 센서 | LDS-02 LiDAR, OpenCR, C920 | D405 |
| 전원 | OpenCR 5 V | **따로 공급 (아래 4장)** |

### 고려 사항
- **시간 동기화**: 두 Pi의 시계가 어긋나면 TF와 센서 융합이 깨집니다. 라파1을 기준으로 `chrony`를 맞춥니다.
- **네트워크 대역폭**: 영상 원본을 Wi-Fi로 보내지 않습니다. 라파2 안에서 VSLAM까지 처리하고, 결과(자세, 지도)만 보냅니다.
- **TF**: D405의 장착 위치(`base_link → camera_link`)를 실측해서 static TF로 넣습니다.

## 4. 전원 (라파2)
- 라파1과 같은 OpenCR 5 V에 함께 물리지 않는 것을 원칙으로 합니다.
- 후보
  1. **USB-PD 보조배터리 (5 V 5 A 지원)**: 배선이 가장 간단하고, Pi 5의 USB 전류 제한(600 mA)도 피할 수 있습니다.
  2. 로봇 배터리(11.1 V) → **DC-DC 5 V 5 A 강압 모듈** → Pi 5: 배터리 하나로 끝나지만 주행 시간이 줄어듭니다.
- 확인할 것
  - 로봇 배터리 주행 시간: 10-02에 11.3 V(31 %)에서 노드가 죽은 기록이 있습니다.
  - Pi 2대 + D405 + 터치 화면을 다 켰을 때 소비 전력을 실측합니다.

## 5. D405 특성과 주의점

| 항목 | 값 (제조사) |
|---|---|
| 최적 거리 | **7 ~ 50 cm** (근거리용) |
| 깊이 정확도 | 50 cm에서 ±2 % |
| 시야각 | 87° × 58° |
| 셔터 | 글로벌 셔터 |
| 해상도 / 프레임 | 최대 1280×720 / 최대 90 fps |
| 전력 | 스트리밍 약 1.55 W |
| IMU | 없음 (D435i·D455와 다름) |

- **D405는 원래 근거리 작업용**(로봇 팔 집기 등) 카메라입니다. 방 규모 VSLAM에서는 이런 한계가 있습니다.
  - 50 cm 넘는 벽이나 가구는 깊이 정확도가 빠르게 떨어집니다.
  - 그래서 깊이로 지도를 만드는 것보다는 **영상 특징점(시각 주행거리, 루프 클로저)** 쪽에 기대게 됩니다.
  - IMU가 없어서 빠르게 회전하면 추적을 놓치기 쉽습니다. 로봇 바퀴 odom으로 보완합니다.
- 장착
  - 앞을 보게 달되, LiDAR의 360° 시야를 가리지 않게 합니다.
  - 근거리 장점을 살리려면 약간 아래로 기울여서 바닥 앞쪽 장애물을 보게 하는 방안도 검토합니다. 13 cm보다 낮은 물체는 LiDAR가 못 보기 때문에 그걸 보완하는 역할입니다.
- 결과가 부족하면 D435i나 D455(원거리 + IMU)로 바꾸는 것도 교수님께 같이 말씀드립니다.

## 6. 소프트웨어 후보

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **RTAB-Map** (`rtabmap_ros`) | ROS 2 Jazzy 패키지 있음. RGB-D와 **LiDAR 스캔을 함께** 쓸 수 있음. 루프 클로저 지원. 2D occupancy 지도도 출력 | Pi 5에서는 해상도·주기를 낮춰야 함 | **1순위** |
| ORB-SLAM3 | 시각 SLAM 정확도가 높음 | ROS 2 공식 지원이 없어 직접 빌드해야 함 | 비교용 후보 |
| Isaac ROS VSLAM | 빠름 | NVIDIA Jetson 전용 | 제외 |

- **D405 드라이버**: `librealsense2` + `realsense2_camera`
  - Pi 5(ARM64)·Ubuntu 24.04에서는 바이너리가 없을 수 있어서 소스 빌드(RSUSB 백엔드)를 생각해 둡니다.
  - 받으면 가장 먼저 확인할 위험 요소입니다.

## 7. "함께" 진행하는 방식
1. **A안: 따로 돌리고 비교** (먼저)
   - LiDAR: 지금의 Cartographer 지도 + AMCL
   - VSLAM: RTAB-Map(RGB-D만 사용)으로 같은 방의 지도와 궤적을 따로 만듭니다.
   - 같은 경로를 주행하면서 두 위치 추정을 비교합니다.
2. **B안: 융합**
   - RTAB-Map에 LiDAR `/scan` + D405 + 바퀴 odom을 함께 넣습니다.
   - LiDAR가 2D 구조를 잡고, 카메라가 루프 클로저와 낮은 장애물을 보완합니다.
   - 결과 지도를 Nav2에 쓸지는 A안 결과를 보고 정합니다.

## 8. 진행 순서 (안)

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 0 | 라파2 준비 (Ubuntu 24.04 + Jazzy, 라파1과 같은 설정), 전원 결정 | 라파2에서 `ros2 topic list`로 라파1 토픽이 보임 |
| 1 | D405 드라이버 설치 | `/camera/.../image_rect_raw`, depth 토픽 30 fps 확인 |
| 2 | 장착 + static TF + 시간 동기화 | RViz에서 카메라 점군이 LiDAR 스캔과 겹침 |
| 3 | RTAB-Map RGB-D 단독 (A안) | 방 한 바퀴 지도, 루프 클로저 성공 |
| 4 | LiDAR SLAM과 비교 | 같은 경로에서 두 궤적 오차 비교표 |
| 5 | LiDAR + 카메라 융합 (B안) | 융합 지도로 위치 추정, 오차가 4단계 이하 |
| 6 | Nav2·음성 이동과 연결 여부 결정 | 기존 1~5번 장소 이동이 유지됨 |
